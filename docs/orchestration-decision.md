# Orchestration Decision: нужен ли LangGraph?

Дата: 2026-10-28. Вопрос: оправдан ли LangGraph для agent-режима AI-RAG-Chat
сегодня? Короткий ответ: **нет** — с конкретными условиями, при которых
переоценить.

## 1. Текущая orchestration (по коду)

`app/core/agent.py` (~180 строк) — собственный ReAct-цикл:

```
START → [LLM: JSON action] ──→ tool (list_documents | search_documents)
              ↑                        │  observation добавляется в messages
              └────────────────────────┘   (цикл, максимум MAX_STEPS=5)
              │
   action.final==true → sources → потоковый answer → agent_meta → END
              │
   невалидный JSON → один "nudge" (формат-подсказка) → снова цикл
              │
   исчерпаны 5 шагов → fallback: один search + классический RAG-ответ → END
```

Состояния и свойства:
- **Состояния**: неявные — «think/act» и «final»; состояние цикла — просто
  растущий `messages` + `accumulated_hits` + `steps`.
- **Переходы**: линейные, один цикл с жёстким счётчиком; recovery-ветка при
  drift модели; гарантированный fallback на классический RAG.
- **Persistence**: `steps` и `sources` сохраняются в `Message.agent_steps/sources`
  (SQLite) после завершения; промежуточного checkpointing нет — и не нужно:
  потерянный цикл ≤5 шагов дешевле перезапустить, чем восстанавливать.
- **Human-in-the-loop**: отсутствует; агент read-only (list/search), side
  effects невозможны — HITL нечего утверждать.
- **Тестируемость**: полный мок-путь (offline demo) + `tests/test_agent.py`
  с fake-провайдерами; детерминированный fallback.

## 2. Сравнение: собственный цикл vs минимальный LangGraph

| Критерий | Текущий цикл | LangGraph StateGraph |
|---|---|---|
| LOC / слоёв | ~180 строк, 0 зависимостей | граф-декларация + runtime; +`langgraph`/`langchain-core` (~30+ транзитивных пакетов) |
| Тестируемость | прямой async-генератор, fake providers уже в тестах | тестирование через checkpointer/моки фреймворка |
| Streaming | нативный SSE-генератор (`yield`) | эмуляция через stream events (дополнительный слой трансляции в текущий SSE-протокол) |
| Persistence/HITL | нет (не нужен — read-only, ≤5 шагов) | главная ценность LangGraph — здесь не востребована |
| Observability | steps уже пишутся в БД | LangSmith-интеграция — но она оценена и отложена (см. ниже) |
| Риск | собственный код, но тривиальный и покрытый | версия-цикл фреймворка, миграции API, поставка вместе с langchain-экосистемой |
| Что реально улучшит | — | checkpointing и resumable-графы: ценно при длинных multi-агентных сценариях, которых в проекте нет |

## 3. Критерии, при которых LangGraph станет оправдан

1. Агенту нужны **write-инструменты** или side effects → потребуется HITL и
   checkpointing перед действием.
2. **Multi-агент/многофазные** workflows (например: planner → retriever →
   verifier → writer) с восстановлением после падения посреди цепочки.
3. Долгие циклы (шаги десятки, не 5), где персистентность промежуточного
   состояния экономит реальные токены/время.
4. Появится LangSmith/Langfuse-observability production-трафика — тогда общий
   runtime упрощает трассировку (но это отдельное решение, см. решение Stage 3:
   не интегрировать сейчас).

Ни один из критериев сегодня не выполнен: инструменты read-only, цикл ограничен
пятью шагами, каждый шаг виден пользователю в UI, fallback детерминирован.

## 4. Решение

**Оставить существующую orchestration.** Она проще, полностью покрыта тестами,
не добавляет зависимостей и закрывает все текущие сценарии. LangGraph здесь —
решение проблемы, которой нет, ценой существенной новой зависимости и слоя
трансляции SSE. Переоценка — при появлении любого из критериев §3.

Migration cost (если когда-нибудь понадобится): перенос цикла в StateGraph —
оценочно 1–2 дня; текущие SSE-события (`agent_step`/`sources`/`token`) сохраняются
как контракт фронтенда, что смягчает будущую миграцию.
